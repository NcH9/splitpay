# Посібник користувача SplitPay

SplitPay надає **вебінтерфейс (Twig + Bootstrap 5)** та **HTTP JSON API** для реєстрації користувачів, створення замовлень, спліт-оплат із вибором стратегії синхронізації та живого бенчмаркінгу конкурентності.

> Система моделює облік платежів і механізми синхронізації (PostgreSQL, Redis, RabbitMQ). Вона не звертається до реального банківського еквайрингу, не списує кошти та не підтверджує фактичне отримання готівки.

## Запуск локального середовища

Потрібен Docker із Compose. У корені проєкту виконайте:

```bash
docker compose up -d --build
docker compose exec php php bin/console doctrine:migrations:migrate --no-interaction
```

Стек підіймає 5 контейнерів: `php` (PHP 8.4 FPM), `nginx`, `database` (PostgreSQL 16), `redis` (Redis 7) та `rabbitmq` (RabbitMQ 3 із Management UI).

Корисні адреси після запуску:
- **Вебінтерфейс та API:** `http://localhost:8080`
- **RabbitMQ Management UI:** `http://localhost:15672` (логін/пароль за замовчуванням: `guest` / `guest`)

> Значення в `.env` призначені для локальної розробки; перед розгортанням у спільному чи виробничому середовищі задайте власні секрети й облікові дані в `.env.local`.

### Обробка асинхронних подій (RabbitMQ)

Після успішного платежу застосунок публікує події `PaymentReceivedEvent` та `OrderFullyPaidEvent` (якщо замовлення сплачено повністю) у чергу RabbitMQ (`splitpay_async`). Щоб запустити воркер обробки чеків і вебхуків у реальному часі, виконайте в окремому терміналі:

```bash
docker compose exec php php bin/console messenger:consume async -vv
```

У разі тимчасової помилки обробки повідомлення повторюється до 3 разів з експоненційною затримкою (1с → 2с → 4с), після чого потрапляє до Dead Letter Queue (`splitpay_failed`).

## Вебінтерфейс (Web UI)

Відкрийте `http://localhost:8080` у браузері:

- **`/` або `/dashboard`** — головна панель: зведена статистика за замовленнями й сумами, таблиця всіх замовлень, швидке створення користувачів (`POST /web/users`) і замовлень (`POST /web/orders`) через модальні вікна.
- **`/web/orders/{id}`** — картка замовлення: прогрес-бар оплати, версія ORM, історія проведених транзакцій, форма внесення поодинокого платежу з вибором користувача, способу оплати (`card`/`cash`), стратегії синхронізації й генерацією `idempotency_key`, а також **Симулятор конкурентної мультикористувацької оплати**.
- **`/benchmark`** — інтерактивний модуль дослідження стратегій: дає змогу запустити паралельний стрес-тест прямо з браузера (зокрема з полем **`users_count`** — «Учасники (Users)» від 1 до 50 платників у режимі round-robin із чергуванням `card`/`cash`) та побачити метрики (`RPS`, `P50`/`P95`/`P99`, розподіл HTTP-кодів і результати аудиту інваріантів I1–I5).

> У вебформах суми вводяться у доларах (наприклад, `125.00`), а на сервері автоматично переводяться у цілі центи.

### Симулятор конкурентної мультикористувацької оплати (`/web/orders/{id}`)

На сторінці конкретного замовлення доступна панель **«Симулятор конкурентної мультикористувацької оплати»** (`POST /web/orders/{id}/simulate-concurrent`), яка дає змогу змоделювати одночасну оплату одного замовлення кількома різними учасниками:

- **Серверна паралельність (`curl_multi`):** запити надсилаються паралельно з бекенда до HTTP API (`POST /payments/{orderId}`), що оминає браузерне обмеження (~6 одночасних з’єднань) і створює реальну конкуренцію у PHP-FPM та PostgreSQL.
- **Конфігурація учасників:** можна обрати стратегію синхронізації (`atomic`, `pessimistic`, `optimistic`, `mutex`, `baseline`), задати ліміт паралельності (`concurrency`, 1–50 або автоматично за кількістю рядків) та налаштувати для кожного рядка окремого платника (`user_id`), суму в доларах і спосіб оплати (`card` або `cash`).
- **Швидкі пресети та керування рядками:**
  - **«+ Додати учасника»** — додає новий рядок платника;
  - **«Розділити залишок порівну»** — рівномірно розподіляє поточний залишок замовлення між наявними користувачами (залишкові центи додаються до першого рядка);
  - **«Симулювати конфлікт (переплата)»** — заповнює 2+ рядки різними користувачами так, щоб кожен намагався одночасно сплатити ≥ 65% залишку (сумарно більше за доступний баланс), демонструючи роботу інваріантів I1–I4 або гонку даних у `baseline`.
- **Таблиця результатів та аудит:** після виконання симуляції відображається панель результатів із лічильником унікальних учасників, статистикою HTTP-кодів (`201 Created`, `409 Conflict`, `422 Unprocessable`, `5xx`), затримками `P50 / P95 мс`, `RPS`, вердиктами `ConsistencyAuditor` для **I1 (No Overpayment)** та **I2 (Balance Integrity)** (`ЗБЕРЕЖЕНО` / `ПОРУШЕНО`), а також детальною таблицею кожної спроби (`#`, `Учасник`, `Сума`, `Спосіб`, `HTTP Статус`, `Затримка (мс)`, `Платіж / Помилка`, `Idempotency Key`).

## Як працює оплата через API

Спочатку створіть користувача, потім замовлення із загальною вартістю та `userId` власника, після чого реєструйте один або кілька платежів. Стан замовлення та зареєстровані платежі можна прочитати окремими запитами.

Усі грошові значення в JSON API передаються **цілими числами** в найменших одиницях валюти: наприклад, `1050` означає `10.50`. API не зберігає код валюти, тому клієнт має стежити, щоб в одному замовленні не змішувалися валюти. Дозволені лише додатні суми.

`paymentMethod` приймає `card` або `cash`.

### Ідемпотентність (Redis Pre-Filter)

Запити проходять швидку перевірку в **Redis** (`SET NX EX`) ще до відкриття транзакції в PostgreSQL:
1. Під час отримання запиту ключ `idempotency:{key}` атомарно блокується на 60 секунд. Повторний паралельний запит із тим самим ключем миттєво відхиляється зі статусом `409 Conflict`.
2. Після успішної оплати ключ зберігається в Redis на **24 години**.
3. Якщо платіж відхилено через бізнес-помилку (наприклад, `422` за переплату або `404`), тимчасове блокування ключа знімається, щоб клієнт міг виправити суму й повторити спробу.

## HTTP API

Для запитів із JSON-тілом передавайте заголовок `Content-Type: application/json`. Успішні відповіді повертаються у форматі JSON.

### Створити користувача

`POST /users`

```json
{
  "name": "Олексій"
}
```

Ім’я обов’язкове, довжина — від 2 до 255 символів. У разі успіху API відповідає `201 Created` і повертає `id`, `name`, `createdAt`.

### Отримати користувача

`GET /users/{id}`

Повертає `id`, `name`, `createdAt`. Для невідомого ID відповідь — `404 Not Found`.

### Створити замовлення

`POST /orders`

```json
{
  "name": "Вечеря",
  "fullPriceCents": 12500,
  "userId": 1
}
```

`name` — обов’язкова назва довжиною 2–255 символів, `fullPriceCents` — додатна загальна сума, `userId` — ID наявного користувача. У разі успіху API відповідає `201 Created`. Якщо користувача немає, відповідь — `404 Not Found`.

### Отримати замовлення

`GET /orders/{id}`

Приклад відповіді:

```json
{
  "id": 1,
  "name": "Вечеря",
  "fullPriceCents": 12500,
  "paidPriceCents": 5000,
  "remainingCents": 7500,
  "status": "open",
  "version": 2,
  "createdAt": "2026-11-06T12:00:00+00:00",
  "updatedAt": "2026-11-06T12:10:00+00:00"
}
```

`remainingCents` — сума, що залишилася до сплати. Статус нового замовлення — `open`; після повної оплати він змінюється на `paid`. Для невідомого замовлення відповідь — `404 Not Found`.

### Зареєструвати платіж

`POST /payments/{orderId}`

```json
{
  "amountCents": 5000,
  "paymentMethod": "card",
  "idempotencyKey": "order-1-payment-1",
  "userId": 2,
  "strategy": "atomic"
}
```

Обов’язкові поля:

- `amountCents` — додатна сума, що не перевищує залишок замовлення.
- `paymentMethod` — `card` або `cash`.
- `idempotencyKey` — непорожній рядок завдовжки до 255 символів. Створюйте нове унікальне значення для кожної окремої спроби оплати. Якщо повторюєте той самий запит після збою мережі, використовуйте попередній ключ: повторний запис буде відхилено, а не продубльовано.
- `userId` — ID наявного користувача, який вносить платіж. Наразі API не перевіряє, чи є він власником замовлення.
- `strategy` — необов’язковий параметр. Допустимі значення: `atomic`, `pessimistic`, `optimistic`, `mutex`, `baseline`. За замовчуванням використовується `baseline`.

Для звичайної реєстрації платежів використовуйте `atomic`, `pessimistic`, `optimistic` або `mutex` (використовує розподілене блокування через Redis). `baseline` залишено для демонстрації змагань за ресурс під час паралельних запитів.

Успішна відповідь — `201 Created`; вона містить ID платежу й замовлення, ID користувача, суму, спосіб оплати, ключ ідемпотентності, вибрану стратегію, кількість повторів (`retriesAttempted`) та час створення.

### Отримати платіж

`GET /payments/{id}`

Повертає запис платежу. Для невідомого ID відповідь — `404 Not Found`.

## Помилки API

| HTTP-код | Значення |
|---|---|
| `404 Not Found` | Не знайдено користувача, замовлення або платежу, вказаного в запиті. |
| `409 Conflict` | Замовлення вже закрите для платежів, ключ ідемпотентності вже використано, або вичерпано ліміт повторів оптимістичного блокування. |
| `422 Unprocessable Entity` | Помилка перевірки полів або сума платежу перевищує доступний залишок. |

У разі помилки перевірте JSON, типи полів і допустимі значення. Зокрема, ідентифікатори й грошові суми мають бути числами, а не рядками.

## Benchmark стратегій (CLI та Web UI)

Окрім вебінтерфейсу (`/benchmark`), у проєкті є консольна команда для навантажувального порівняння. Вона створює тестового користувача (або групу з `--users` різних платників) і замовлення, надсилає паралельні HTTP-запити до локального Nginx і звіряє збережені суми із сумою записів платежів.

Приклад запуску в PHP-контейнері (однокористувацький та мультикористувацький режими):

```bash
docker compose exec php php bin/console app:benchmark:run \
  --strategy atomic \
  --users 5 \
  --requests 50 \
  --concurrency 10 \
  --order-full-price 10000 \
  --payment-amount 1000 \
  --format table
```

Параметри `--users` (за замовчуванням `1`), `--requests`, `--concurrency`, `--order-full-price` і `--payment-amount` мають бути додатними цілими числами. Якщо `--users > 1`, команда створює вказану кількість окремих користувачів, розподіляє запити між ними за схемою round-robin із чергуванням способів оплати `card` та `cash` і додає колонку `Users` у вивід `table` / `markdown`. `--format` приймає `table`, `markdown` або `json`. Щоб порівняти всі реалізації, вкажіть `--strategy all`. Команда підтримує стратегії `baseline`, `pessimistic`, `optimistic`, `mutex`, `atomic`.

Benchmark створює постійні записи в підключеній базі даних і призначений для локальної розробки. Не запускайте його проти робочої бази.

## Що наразі не підтримується

- Немає реєстрації/входу, перевірки прав доступу (автентифікації) та CSRF-токенів у вебформах. Усі маршрути API та вебінтерфейсу доступні без автентифікації; не публікуйте цей екземпляр у відкритій мережі.
- Немає API-маршрутів для списків користувачів, замовлень чи платежів, зміни й видалення записів, скасування замовлення або розрахунку взаємних боргів між учасниками (список замовлень та історія транзакцій доступні лише у вебінтерфейсі).
- Платіж пов’язується із замовленням і користувачем-внескодавцем, але належність користувача до замовлення не перевіряється.
- Валюта не передається й не зберігається.
- Оплату карткою не інтегровано з платіжним провайдером; надсилання чеків і вебхуків у RabbitMQ-обробниках моделюється записом у журнал (логи).

## Відомі обмеження реалізації

- Стратегія `baseline` навмисно не захищена від змагань за ресурс (виступає контрольною групою в експерименті). Паралельні запити спричиняють розбіжність між сумою замовлення та записами платежів і втрачені оновлення.
- Ключі ідемпотентності унікальні глобально, а не в межах окремого користувача чи замовлення (як і в більшості платіжних API). У разі повторного надсилання того самого ключа система повертає `409 Conflict`.
