# Посібник користувача SplitPay

SplitPay надає HTTP API для реєстрації користувачів, створення замовлень і обліку внесків у замовлення. Вебінтерфейсу немає: надсилайте запити через клієнт API, наприклад `curl`, Postman або власну програму.

> API записує відомості про платіж у базу даних. Він не звертається до банку, не списує кошти та не підтверджує фактичне отримання готівки.

## Запуск локального середовища

Потрібен Docker із Compose. У корені проєкту виконайте:

```bash
docker compose up -d --build
docker compose exec php php bin/console doctrine:migrations:migrate --no-interaction
```

Після запуску API доступне за адресою `http://localhost:8080`. PostgreSQL у локальному Compose використовує значення за замовчуванням із `.env`. Це налаштування для розробки; перед розгортанням у спільному чи виробничому середовищі задайте власні секрети й облікові дані.

## Як працює оплата

Спочатку створіть користувача, потім замовлення із загальною вартістю та `userId` власника, після чого реєструйте один або кілька платежів. Стан замовлення та зареєстровані платежі можна прочитати окремими запитами.

Усі грошові значення передаються цілими числами в найменших одиницях валюти: наприклад, `1050` означає 10,50 одиниці валюти. API не зберігає код валюти, тому клієнт має стежити, щоб в одному замовленні не змішувалися валюти. Дозволені лише додатні суми.

`paymentMethod` приймає `card` або `cash`. Це позначка способу оплати в записі, а не операція оплати карткою.

## API

Для запитів із JSON-тілом передавайте заголовок `Content-Type: application/json`. Успішні відповіді повертаються у форматі JSON.

### Створити користувача

`POST /users`

```json
{
  "name": "Олексій"
}
```

Ім’я обов’язкове, довжина — від 2 до 255 символів. У разі успіху API відповідає `201 Created` і повертає `id`, `name`, `createdAt`.

### Отримати користувача

`GET /users/{id}`

Повертає `id`, `name`, `createdAt`. Для невідомого ID відповідь — `404 Not Found`.

### Створити замовлення

`POST /orders`

```json
{
  "name": "Вечеря",
  "fullPriceCents": 12500,
  "userId": 1
}
```

`name` — обов’язкова назва довжиною 2–255 символів, `fullPriceCents` — додатна загальна сума, `userId` — ID наявного користувача. У разі успіху API відповідає `201 Created`. Якщо користувача немає, відповідь — `404 Not Found`.

### Отримати замовлення

`GET /orders/{id}`

Приклад відповіді:

```json
{
  "id": 1,
  "name": "Вечеря",
  "fullPriceCents": 12500,
  "paidPriceCents": 5000,
  "remainingCents": 7500,
  "status": "open",
  "version": 2,
  "createdAt": "2026-11-06T12:00:00+00:00",
  "updatedAt": "2026-11-06T12:10:00+00:00"
}
```

`remainingCents` — сума, що залишилася до сплати. Статус нового замовлення — `open`; після повної оплати він змінюється на `paid`. Для невідомого замовлення відповідь — `404 Not Found`.

### Зареєструвати платіж

`POST /payments/{orderId}`

```json
{
  "amountCents": 5000,
  "paymentMethod": "card",
  "idempotencyKey": "order-1-payment-1",
  "userId": 2,
  "strategy": "atomic"
}
```

Обов’язкові поля:

- `amountCents` — додатна сума, що не перевищує залишок замовлення.
- `paymentMethod` — `card` або `cash`.
- `idempotencyKey` — непорожній рядок завдовжки до 255 символів. Створюйте нове унікальне значення для кожної окремої спроби оплати. Якщо повторюєте той самий запит після збою мережі, використовуйте попередній ключ: повторний запис буде відхилено, а не продубльовано.
- `userId` — ID наявного користувача, який вносить платіж. Наразі API не перевіряє, чи є він власником замовлення.
- `strategy` — необов’язковий параметр. Допустимі значення: `atomic`, `pessimistic`, `optimistic`, `mutex`, `baseline`. За замовчуванням використовується `baseline`.

Для звичайної реєстрації платежів використовуйте `atomic`, `pessimistic` або `mutex`. `baseline` залишено для демонстрації змагань за ресурс під час паралельних запитів.

Успішна відповідь — `201 Created`; вона містить ID платежу й замовлення, суму, спосіб оплати, ключ ідемпотентності, вибрану стратегію та час створення.

### Отримати платіж

`GET /payments/{id}`

Повертає запис платежу. Для невідомого ID відповідь — `404 Not Found`.

## Помилки

| HTTP-код | Значення |
|---|---|
| `404 Not Found` | Не знайдено користувача або замовлення, вказаного в запиті. |
| `409 Conflict` | Замовлення вже закрите для платежів або ключ ідемпотентності вже використано. Також можливий конфлікт паралельного оновлення. |
| `422 Unprocessable Entity` | Помилка перевірки полів або сума платежу перевищує доступний залишок. |

У разі помилки перевірте JSON, типи полів і допустимі значення. Зокрема, ідентифікатори й грошові суми мають бути числами, а не рядками.

## Benchmark стратегій

У проєкті є консольна команда для навантажувального порівняння. Вона створює тестового користувача й замовлення, надсилає паралельні HTTP-запити до локального Nginx і звіряє збережені суми із сумою записів платежів.

Приклад запуску в PHP-контейнері:

```bash
docker compose exec php php bin/console app:benchmark:run \
  --strategy atomic \
  --requests 50 \
  --concurrency 10 \
  --order-full-price 10000 \
  --payment-amount 1000 \
  --format table
```

Параметри `--requests`, `--concurrency`, `--order-full-price` і `--payment-amount` мають бути додатними цілими числами. `--format` приймає `table`, `markdown` або `json`. Щоб порівняти всі реалізації, вкажіть `--strategy all`. Команда підтримує стратегії `baseline`, `pessimistic`, `optimistic`, `mutex`, `atomic`.

Benchmark створює постійні записи в підключеній базі даних і призначений для локальної розробки. Не запускайте його проти робочої бази.

## Що наразі не підтримується

- Немає інтерфейсу користувача, реєстрації/входу та перевірки прав доступу. Усі маршрути API доступні без автентифікації; не публікуйте цей екземпляр у відкритій мережі.
- Немає маршрутів для списків користувачів, замовлень чи платежів, зміни й видалення записів, скасування замовлення або розрахунку взаємних боргів між учасниками.
- Платіж пов’язується із замовленням і користувачем-внескодавцем, але належність користувача до замовлення не перевіряється.
- Валюта не передається й не зберігається.
- Оплату карткою не інтегровано з платіжним провайдером; запис `card` сам по собі не означає, що кошти списано.

## Відомі обмеження реалізації

- Стратегія `baseline` навмисно не захищена від змагань за ресурс (виступає контрольною групою в експерименті). Паралельні запити спричиняють розбіжність між сумою замовлення та записами платежів і втрачені оновлення.
- Ключі ідемпотентності унікальні глобально, а не в межах окремого користувача чи замовлення (як і в більшості платіжних API). У разі спроби повторного надсилання однакового ключа система повертає `409 Conflict`.
